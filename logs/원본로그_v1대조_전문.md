```

[관계·직급] 2년차 계약 고객사, 실무 담당자
[메일 목적] 어제 발생한 서비스 장애에 대한 사과 및 후속 조치 안내

- 장애 일시: 2026-07-26 14:10 ~ 16:35 (KST)
- 원인: 데이터베이스 이중화 전환 중 설정 오류
- 영향: 대시보드 조회 불가. 데이터 유실은 없음(백업 검증 완료)
- 조치: 전환 절차에 사전 검증 단계 추가 완료
[핵심 포인트 3개]
1. 데이터 유실은 없었다는 점을 분명히 할 것

[금지어] "죄송하지만", "어쩔 수 없이", "일시적 현상"
[필수 포함 항목] 장애 시간, 데이터 유실 없음, 재발 방지 조치, 회신 요청
[마감·회신기한] 2026-07-29(수) 오후 6시까지 회신 요청
```

## 관찰 기록 (출력을 본 뒤 작성)

### 예상과 달랐던 점 — 먼저 적는다

설계 단계에서 "v1은 지정 금지어를 위반할 것"이라고 예상했으나, **실제로는 금지어 3개(`죄송하지만`/`어쩔 수 없이`/`일시적 현상`)를 모두 지켰다.** 금지어가 입력 텍스트 안에 명시돼 있었기 때문으로 보인다. 예상이 빗나간 부분이므로 그대로 기록하고, [02_시스템설계문서.md](../02_시스템설계문서.md) 6.2절의 문제 목록에서도 이 항목을 제외했다.

즉 **v1의 문제는 "글을 못 쓴다"가 아니다.** 문장 자체는 그대로 보내도 될 만큼 매끄럽다. 문제는 다른 데 있었다.

### 실제로 관찰된 문제

| # | 문제 | 해당 부분 | 왜 문제인가 |
|---|---|---|---|
| **P1** | **입력에 없는 상태를 단정** — "보상 방안을 **검토 중**이며" | 본문 4문단 | 사용자가 준 것은 "보상 관련 협의를 제안할 것"뿐이다. 사내에서 실제로 검토가 시작됐는지는 아무도 말한 적이 없다. 고객사가 이 문장을 근거로 보상을 기대하면 분쟁 소지가 된다 |
| **P2** | **근거 없는 약속** — "앞으로도 안정적인 서비스 제공을 위해 **최선을 다하겠습니다**" | 본문 3문단 | 관용구지만 계약 문서에서는 이행 약속으로 읽힐 수 있다. 사용자가 요청한 적 없는 문장이다 |
| **P3** | **형식 없음** — 제목 1개, 다음 액션 없음, 확인 필요 블록 없음 | 출력 전체 | 사용자가 무엇을 골라야 하는지, 발송 전에 무엇을 해야 하는지 알 수 없다 |
| **P4** | **확인된 것과 확인 안 된 것이 한 문단에 섞임** | 본문 4문단 | 장애 시간(확인됨)과 보상 검토 상태(미확인)가 같은 문단에 나란히 있다. **주니어 담당자는 이 둘을 구분할 방법이 없다.** 이것이 v1의 가장 큰 실패다 |
| **P5** | 사과 표현 3회 (사과드립니다 / 불편을 드린 / 죄송합니다) | 본문 1·5문단 | 담백한 톤 요청과 어긋난다. 과잉 사과는 책임 범위를 흐린다 |

### 핵심 진단

> v1의 실패는 **문장 품질이 아니라 검증 가능성**에 있다.
> 확인된 사실과 모델이 채워 넣은 문장이 같은 문단에 섞여 나오면, 사람이 발송 전에 무엇을 확인해야 하는지 알 수 없다. P1·P2는 각각 한 문장씩이라 눈에 잘 띄지도 않는다.
>
> 이는 [02_시스템설계문서.md](../02_시스템설계문서.md) 0.1절에서 정리한 "모델에는 **모른다**에 해당하는 상태가 없다"가 그대로 나타난 사례다. 보상 관련 정보가 비어 있는 자리에도 다음 토큰 확률은 존재했고, 그래서 "검토 중"이라는 그럴듯한 문장이 채워졌다.

### v2로 넘어가며 결정한 것

문제가 "빈칸을 채워 버리는 것"이라면, 해결책은 **빈칸을 담을 그릇을 미리 만들어 주는 것**이다. → v2의 `4. 확인 필요` 블록과 `[출처 확인 필요]` 태그가 여기서 나왔다.
